## 1. Архитектура и стек

### 1.1. Главное решение: на чём строить просмотрщик

Сравнивались два варианта.

**Вариант А — `androidx.pdf` 1.0.0-beta01** (`PdfViewerFragment` / `EditablePdfViewerFragment`).

| Плюсы | Минусы |
|---|---|
| Готовы: отрисовка, масштаб и тайлинг, поиск, выделение, заполнение форм, перо, маркер, ластик, undo/redo. Чтение и пометки уже работают «из коробки». | Статус beta. `EditablePdfViewerFragment`, `AnnotationsView` и `PdfViewer` помечены `@ExperimentalPdfApi`, так что API ещё могут измениться. **[проверено]** |
| Сохранение через `applyDraftEdits()` → `onApplyEditsSuccess(PdfWriteHandle)`. **[проверено]** | Редактирование требует `@RequiresExtension(extension = 31, version = 18)` (S Extensions 18). Это то же условие, что и для нативного API пометок (см. 1.2), так что преимущества здесь нет. **[проверено]** |
| | В примечаниях к релизам нет **постраничного горизонтального листания** (FR-10б) и **текстовых заметок** (FR-28). Их всё равно пришлось бы писать самим поверх чужого фрагмента. **[проверено: в release notes не упоминаются]** |
| | Много транзитивных зависимостей (androidx.ink, fragment, Compose-часть). Для Compose-части нужен AGP ≥ 9.2.0, потому что она собрана с compileSdk 37. **[проверено]** При сборке «вслепую» каждая лишняя зависимость повышает риск. |
| | Fragment-based API плохо сочетается с полностью Compose-интерфейсом. Внешний вид («красивый» стиль, тёмная тема) настраивается ограниченно. |

**Вариант Б — свой просмотрщик на встроенном `android.graphics.pdf.PdfRenderer` (API 35+)**, без сторонних PDF-библиотек.

| Плюсы | Минусы |
|---|---|
| Стабильный платформенный API, ноль внешних PDF-зависимостей, лицензионных вопросов нет. | Больше своего кода: тайлинг, жесты, маркеры выделения текста, наложение форм, инструменты пометок. |
| В API 35 есть всё нужное для чтения, поиска, выделения и форм. В `PdfRenderer.Page` добавлены `searchText`, `selectContent`, `getTextContents`, `getGotoLinks`, `getLinkContents`, `getFormWidgetInfos`, `applyEdit`, `render(Bitmap, Rect, Matrix, RenderParams)`. Запись выполняет `PdfRenderer.write()`. **[проверено]** | API пометок появился только в **36.1** (Android 16 QPR2) или на устройствах с **S Extensions 18** (см. 1.2). |
| Полный контроль над UX: оба режима листания, ночной режим, заметки, «красивый» Compose-интерфейс. | Оглавления (outline) в API нет, его нужно разбирать самим. **[предположение: в списках API 35/36.1 методов outline нет]** |
| Расчётная логика (геометрия, тайлы, цвет) уходит в чистый JVM-модуль и покрывается тестами. Это прямо соответствует правилам проекта. | |

**Рекомендация: вариант Б.** Причины: (1) ключевые FR-10б и FR-28 в androidx.pdf всё равно отсутствуют; (2) для записи пометок оба варианта упираются в одно и то же условие (S Ext 18); (3) минимум зависимостей снижает риск при слепой сборке; (4) проще выдержать правило «расчётный код отдельно и с тестами». Работа с `PdfRenderer` изолируется за собственным интерфейсом `PdfEngine`. Если позже появится стабильный androidx.pdf, интерфейс позволит заменить реализацию.

### 1.2. Запись пометок в PDF (FR-29): что проверено

- **[проверено]** В API 35 у `PdfRenderer.Page` нет методов для аннотаций. Есть только формы (`applyEdit`) и запись документа `write()`.
- **[проверено]** В **API 36.1** у `PdfRenderer.Page` появились `addPageAnnotation(PdfAnnotation)`, `getPageAnnotations()`, `updatePageAnnotation`, `removePageAnnotation`, `addPageObject`, `getPageObjects` и другие. Пакет `android.graphics.pdf.component` содержит `HighlightAnnotation`, `FreeTextAnnotation`, `StampAnnotation`, `PdfPagePathObject`, `PdfPageImageObject` и `PdfPageTextObject`. В документации сказано: «PdfRenderer.write needs to be called to get the updated PDF stream». В `RenderParams` 36.1 добавлены флаги `FLAG_RENDER_FREETEXT_ANNOTATIONS` и `FLAG_RENDER_STAMP_ANNOTATIONS`.
- **[проверено]** Те же методы есть у `PdfRendererPreV.Page` с пометкой «Also in S Extensions 18». Значит, они могут быть доступны и на Android 15, если модуль PDF обновлён через системные обновления Google Play.
- **[проверено]** Класса **Ink-аннотации в платформенном API нет**. Есть только Highlight, FreeText и Stamp.
- **[предположение]** Росчерки пера можно сохранить как `StampAnnotation` с вложенными `PdfPagePathObject` (вероятно, так работает и androidx.pdf). Другие просмотрщики покажут такую аннотацию как штамп с рисунком: она видна, но это не `/Ink`. Текстовая заметка (FR-28) сохраняется как `FreeTextAnnotation`: в других программах она видна как текстовая рамка, а не как значок-«стикер» `/Text`.
- **[предположение]** Будет ли `PdfRendererPreV` с S Ext 18 работать на Android 15 (API 35) и достигнута ли ext 18 на телефоне пользователя, неизвестно. Это проверяет спайк (этап 1).

**Принятый путь (с развилкой G1 после спайка):**

- **Путь П (платформенный).** Если на телефоне пользователя `SDK_INT_FULL ≥ 36.1` или `SdkExtensions.getExtensionVersion(S) ≥ 18`: Highlight, FreeText и Stamp+Path сохраняются через `addPageAnnotation` → `write()`.
- **Путь С (собственный, запасной и возможный основной).** Модуль `:core` получает минимальный разборщик PDF и писатель **инкрементального обновления** (ISO 32000-1 §7.5.6). Он дописывает в конец файла настоящие `/Ink`, `/Highlight` и `/Text` (стикер с `/Popup`) с потоками внешнего вида `/AP`. Плюсы: стандартные типы (точнее соответствует FR-29), работа на любом Android 15, исходные байты файла не меняются, логика тестируется на JVM. Минусы: больше кода. Этот же разборщик нужен для оглавления (FR-15), поэтому его задача (C2.5) выполняется в любом случае.
- **Решение G1** принимает пользователь по отчёту спайка. **Рекомендация планировщика по умолчанию: путь С**, потому что он соответствует FR-29 буквально (Ink/Text), а путь П оставить для правки или удаления уже сохранённых пометок на устройствах, где он доступен.
- **Отклонено:** «сплющивание» через `android.graphics.pdf.PdfDocument`. Оно уничтожает текстовый слой, формы и ссылки, а это противоречит FR-20/FR-32.

### 1.4. Слои

```
UI (Compose, :app/ui/…)  ──>  ViewModel (:app/…/vm)  ──>  PdfEngine (:app/engine, обёртка PdfRenderer, один поток)
                                     │                              │
                                     └──────>  :core (чистый Kotlin/JVM) <──┘
     геометрия/тайлы/цвет · недавние/закладки/отпечаток · валидация · undo/redo · модель пометок · PDF-разбор + инкрементальный писатель
```

- `PdfRenderer` не потокобезопасен, и одновременно может быть открыта только одна страница. Поэтому весь доступ к нему идёт через один `Dispatcher` (`limitedParallelism(1)`), а `Page` закрывается сразу после операции.
- Отрисовка тайлами: `render(bitmap, clip, matrix, params)`, LRU-кэш битмапов с бюджетом в байтах (NFR-13/14).
- Внутри `:core` координаты хранятся в **пунктах PDF (1/72″)**, это единица страницы, по аналогии с правилом «СИ внутри». Перевод в пиксели экрана выполняется только на границе UI.
- Безопасное сохранение (FR-38): `write()` или инкрементальное обновление пишет во временный файл в `cacheDir` → проверка открытием через новый `PdfRenderer` → резервная копия оригинала во внутреннем хранилище → запись в URI (`"wt"`) → сверка размера → удаление резервной копии. Если что-то пошло не так, оригинал восстанавливается из резервной копии.

## 4. Порядок запуска агентов

1. **GP:** S0.1 ‖ S0.2 ‖ S0.3 (три worktree) → S0.4 (цикл CI) → **G0** (пользователь ставит APK и присылает данные «Диагностики»).
2. Параллельно после G0:
   - **GP:** K1.1 → (пользователь) → K1.2 → **G1** (вопрос пользователю: путь П / С / С+П);
   - **PMR:** M2.1;
   - **UID:** D3.1 (стиль не спрашивать — уже выбран) → одобрение пользователя → D3.2;
   - **GP:** C2.3 ‖ C2.5 ‖ P6.2.
3. **GP:** C2.2 (после M2.1) → **CFA:** A2.6.
4. **GP:** R4.1 → R4.2 ‖ R4.3 → R4.4 ‖ R4.5 ‖ R4.6 → **CFA:** A4.7.
5. **PMR:** M5.1 (после G1) → **GP:** E5.2 ‖ E5.3 ‖ E5.4 → E5.5 → **CFA:** A5.6.
6. **GP:** P6.1 ‖ P6.3; **FS:** F6.4 → одобрение пользователя → реализация одобренного (GP) → R6.5.

После каждой задачи GP делает push и ждёт зелёный CI, прежде чем сливать параллельные worktree.

## 6. Блокеры (нужно от пользователя)

1. **Репозиторий GitHub** (публичный или приватный) и доступ к нему для push. Без него нельзя пройти даже этап 0.
